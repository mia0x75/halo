# ADR 0014: 站内消息与邮件的分工

## 状态

已接受

## 背景

平台有两类通知通道：

- **邮件**（`internal/platform/notify`，当前只接了 `EmailNotifier`）：账号类事件
  （注册、改密、改邮箱）与工单生命周期，接收人是工单的提交人与审核人；
- **站内消息**（`mm_messages`，本轮新增）：收件箱语义，带未读数与已读状态，
  顶栏的「消息 3」来自这里。

两个通道一度都覆盖同一批事件（工单状态变更、执行完成/失败），提交人既收邮件
又收站内信，同一件事被通知两次。事件侧没有约定谁负责哪条通道，行为随代码漂移。

## 决策

**按「谁需要处理 / 谁需要知道结果」分通道，事件侧显式写明收件人。**

| 事件 | 站内信 | 邮件 |
|------|--------|------|
| 工单创建 | 审核人（待审核待办） | 提交人与审核人 |
| 工单状态变更 | 提交人 | 关闭/审核不通过/审核通过时发双方 |
| 工单执行完成 / 失败 | 提交人 | 提交人与审核人 |
| 工单评论 | 提交人 | 提交人与审核人 |
| 账号类（注册/改密/改邮箱） | — | 当事人 |

具体规则：

1. **站内信给当事人**：需要动手处理的人（审核人待审核）与需要知道结果的人
   （提交人收到审核与执行结果）。
2. **邮件是离线通道与留痕**：重要动作即使当事人在系统里也会收到邮件，
   账号类事件只走邮件。
3. **操作者不收到关于自己动作的通知**：`GlobalMessageWriter` 里比较收件人与
   操作者，相同则跳过。
4. 通道归属写在事件处理器的注释里，新增事件时按同一张表选择收件人。

## 后果

正面：

- 两条通道的职责清晰，新增事件不会再双发；
- 站内信的收件人是「待办」语义，与仪表盘的「待我审核」徽标一致；
- 邮件保持离线留痕能力，不因站内信而删减。

负面：

- 提交人在状态变更时仍会收到邮件与站内信各一条（这是有意的：邮件是离线通道，
  站内信带未读数与跳转链接）；
- 站内信没有分页与全文搜索接口，消息量增长后需要补（当前每次取最近 N 条）。

## 后续

- 邮件通道目前只实现了 `EmailNotifier`；`DingTalkNotifier` 与
  `WeChatNotifier` 仍是占位实现，也没有配置项，接入前不暴露任何入口；
- 站内信目前不支持删除与已读全部，需要时再补。
