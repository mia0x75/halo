# ADR 0013: 面向仪表盘的元数据库表扩展

## 状态

已接受

## 背景

前端仪表盘草图（`dashboard.txt`）需要几类数据，现有 16 张表都答不上来：

- **规则命中明细**：命中结果原先只以文本形式写进 `mm_statements.report`，
  无法按级别或规则聚合，「命中分级」「命中 Top 规则」没有数据来源；
- **站内消息**：`mm_logs` 是全局操作日志，没有收件箱语义与已读状态，
  顶栏的未读数没有来源；
- **异步任务执行**：`internal/worker` 的任务实例只存在内存里，重启即丢，
  执行历史无法追查，「执行必经审计」缺落点；
- **群集分组**：用户的组用角色（`mm_roles`）表达，服务器的组此前没有实体，
  「组间权限隔离」缺少落点。

## 决策

新增四张表，每张配一个领域实体、一套双引擎仓储和一个服务：

| 表 | 作用 | 自然键 / 索引 |
|----|------|---------------|
| `mm_violations` | 规则命中明细 | `(ticket_id)`、`(rule_name)`、`(level, create_at)` |
| `mm_messages` | 站内消息 | `(user_id, read_at)`、`(user_id, create_at)` |
| `mm_tasks` | 异步任务执行 | `(status, scheduled_at)`、`(type)` |
| `mm_groups` | 群集分组 | `uuid`、`name` |

配套的结构调整：

- `mm_clusters` 增加 `group_id`（0 表示未分组），群集归属分组；
- `mm_crons` 增加 `user_id` 与 `cluster_id`，定时任务可追溯「谁配置的、跑在哪个群集」；
- `mm_edges` 增加关系类型 4 `ROLE_TO_GROUP`，角色按分组授权，实现组间权限隔离；
- 规则命中的**规则名**在规则分发处（`validate.Call`）回填：规则处理器只产出描述，
  分发处知道规则名，两处在这里汇合，避免改动 180 多处规则处理器。

## 后果

正面：

- 仪表盘需要的四类数据都有明确来源，且都落在元数据库（双引擎并行实现）；
- 命中明细让规则调优有数据：哪条规则最常命中、命中在哪个级别都能聚合；
- 任务执行有台账，重启不丢历史，失败可追查；
- 群集分组让「组间权限隔离」从概念变成可授权的关系。

负面：

- GraphQL 契约新增了 `RuleHit`、`Message`、`Group` 类型与相关查询/变更；
- `mm_edges` 的关系类型是整数枚举，新增类型要同步 schema 与领域常量；
- `internal/worker` 目前仍是内存调度，本轮只落了表与仓储，接入 worker 持久化
  留作后续（表结构已就位）。

## 后续（已补齐的链路）

四张表最初只通到服务层，随后补齐了写入路径与查询面：

- 群集创建/更新接受 `GroupUUID`，写入 `mm_clusters.group_id`；
- 定时任务记录创建人与目标群集（`mm_crons.user_id/cluster_id`）；
- worker 调度即建 `mm_tasks` 行、执行后回写状态与失败原因，
  GraphQL 暴露 `taskExecutions` / `taskExecutionSummary`；
- 规则引擎适配器（`validate.Adapter`）接通，语句与审核两条链路都能拿到
  目标元数据，命中明细与语句在同一事务落库；
- 新增查询统一标注 `@auth`，避免未登录访问时解析器取凭证 panic。

## 遗留

- 新旧两条校验链路并存：工单审核走 legacy `validate.Run`，语句服务走
  analyzer + adapter。命中明细已改为覆盖写（先删后写），两条链路同时启用
  也不会留下重复明细；
- 保留期清理与每日汇总见 ADR 0015；
- 站内消息与邮件的分工见 ADR 0014。
