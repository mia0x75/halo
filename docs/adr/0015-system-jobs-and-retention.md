# ADR 0015: 系统作业、保留期与调度管理面

## 状态

已接受

## 背景

仪表盘需要「近 7 天趋势」这类按天聚合的数据，而平台此前：

- `halocli statistics`（现已改名 `halocli metrics`）只负责建当天的桶，从不汇总；
- `mm_metrics` 的日桶与 `mm_violations` 的明细都无上限地增长；
- `mm_crons` 存的是调度定义，但**没有任何 API 能新建定时作业**，作业只能直接改库；
- `internal/worker` 启动时读一次 `mm_crons`，之后只跑内存里的任务，
  新建的作业要等进程重启才生效。

于是「每日汇总」与「过期清理」这类系统作业没有落地路径。

## 决策

**把系统作业做成一等公民：作业类型由服务端白名单定义，调度由 `mm_crons` 承载，
执行结果记在 `mm_tasks`，进度与保留期用 `mm_metrics` 表达。**

1. **作业白名单**：GraphQL 暴露 `CronJobEnum`（`METRICS_ROLLUP`、`METRICS_CLEANUP`），
   `createCron` 只接受作业类型，命令由服务端固定映射成 `halocli` 的子命令。
   **不接受自由命令**，避免把「新建定时任务」变成远程命令执行入口。
2. **调度生效**：调度器每 60 秒从库中重新装载可调度的作业（新增的补进来、
   删掉的移除，运行中的任务不受影响），并提供 `worker.Reload()` 供变更后立即装载。
3. **汇总作业**：`halocli metrics rollup --date=YYYY-MM-DD`（缺省昨天）把一天的
   工单状态与规则命中汇总进日指标桶；**幂等**——重跑覆盖同一批桶；
   桶是 gauge（快照）而不是 counter（累计），所以覆盖写语义正确。
4. **完成标记**：`rollup-done`（scope=daily, bucket=日期, gauge=1）写在最后，
   中途失败不会出现该标记，作为增量作业的水位线。
5. **保留期**：`halocli metrics cleanup --days=N` 清理过期日指标桶与命中明细；
   日桶按 `bucket` 字符串比较，命中明细按 `create_at` 比较。
6. **CLI 解析**：worker 执行任务时优先找与主程序同目录的 `halocli`，
   再退回 PATH——部署时两个二进制放在一起即可，不依赖 PATH。
7. **执行留痕**：调度即建 `mm_tasks` 行，执行后回写状态与失败原因。

## 后果

正面：

- 每日汇总与过期清理可以被调度起来，且可观测（`mm_tasks` 有执行记录）；
- 作业命令白名单化，管理面不引入任意命令执行；
- 指标表同时承载「运行时累计」（counter）与「按天快照」（gauge），一个表够用。

负面：

- 汇总与清理依赖 `halocli` 可执行文件与 `HALO_CFG`，部署时必须两者齐备；
- 日桶数量随「指标数 × 保留天数」增长，保留期必须设好，否则清理作业拖太久；
- 单实例调度：多实例部署时同一个作业会被每个实例各跑一次，作业需要幂等
  （汇总与清理都是幂等的，但这靠的是作业设计，不是调度器保证）。

## 后续

- 多实例部署时需要租约（`mm_cursors` 那一类设计），当前靠作业自身幂等；
- 规则维度的命中计数没有进指标表：`ruleHitRules` 直接按窗口聚合明细，
  更准确，也不受「重新校验会重复计数」的影响。
