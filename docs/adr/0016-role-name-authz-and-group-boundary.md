# ADR 0016: 角色按名鉴权、分组作为授权边界

## 状态

已接受

## 背景

平台有两处鉴权语义一直对不上：

1. **角色枚举与种子角色错位**。`RoleEnum`（ADMIN=1、REVIEWER=2、DEVELOPER=3、
   USER=4、GUEST=5）是历史遗留的**自增值**，而 `mm_roles.role_id` 是自增主键，
   种子数据是 Root(1)、Reviewer(2)、Developer(3)、Viewer(4)、User(5)、Guest(6)。
   `@auth` 指令拿枚举值直接和 `role_id` 比较，于是 `USER` 实际授予的是
   **Viewer**（只读角色），`GUEST` 实际授予的是 **User**，真正的 Guest(6)
   反而拿不到任何接口。注册接口把默认角色也挂到了 role_id=4。
2. **分组只是标签**。`mm_groups` 与 `mm_clusters.group_id` 早就在，
   角色到分组的边（`ROLE_TO_GROUP`）也能写，但鉴权路径里从没读过它：
   提交工单只校验「用户→群集」边，分组形同虚设，与「组间权限隔离」的
   战略前提对不上。

同时还有几处实现缺陷让这些路径根本跑不通：

- `mm_edges` 的 `ROLE_TO_GROUP` 没有在 `EdgeEnumMap` 里登记，写出来的边
  `type=0`，读出来也按 `type=0` 匹配，勉强自洽但语义错误；
- 事务里的 `Repos` 没装配 `Group` / `Message` / `Task`，`createGroup`
  直接空指针；
- `revokeGroups` 忽略入参里的分组列表，把该角色的全部分组授权删光。

## 决策

**角色按名字鉴权，分组成为真实的授权边界。**

### 1. 角色用名字而不是自增 ID 表达

- `internal/transport/auth/roles.go` 维护「枚举 → 角色名」的映射：
  `ADMIN → {Root}`、`REVIEWER → {Reviewer}`、`DEVELOPER → {Developer}`、
  `USER → {User, Viewer}`、`GUEST → {Guest}`。
- `@auth` 指令、WebSocket 鉴权、SQL 管理指令的判断都改走
  `transportauth.HasAnyRole` / `IsAdmin`。
- 原因：角色表是可运维的（可读、可展示），自增 ID 只是存储细节；
  用名字表达权限，管理员调整角色表也不会悄悄改掉权限语义。
- 注册账号的默认角色按名字取 `User`，取不到就报错，不再硬编码 ID。

### 2. 群集访问权 = 直接授权 ∪ 角色继承的分组

- `transportauth.ClusterAccessible` 先看「用户→群集」边，看不到再看
  「角色→分组」边：用户任一角色被授予该群集所属分组，即可访问该群集。
- 未分组的群集（`group_id = 0`）不参与分组判断，只认直接授权。
- 群集访问校验点统一收敛到这一个函数：提交工单、改工单、查元数据、
  执行查询、测连通性都走它。
- 用户视角的可见群集列表（`me.Clusters`）也按同一套语义算，
  另给 `me.GrantedClusters` 暴露「直接授权」这一层，方便管理面区分
  「直接给的」和「角色继承的」。

### 3. Root 账号受保护

- 停用 Root 账号、收回 Root 角色都会被拒绝（1403），
  避免把平台锁死在自己之外。
- `option(id)` 补上 `@auth(ADMIN)`：按 UUID 读单个选项原本没有鉴权，
  能被用来试探配置内容。

### 4. 分组删除受约束

- 分组下还有群集时拒绝删除（`domain.ErrConflict`），提示先迁移；
  群集否则会留着悬空的 `group_id`。
- `revokeGroups` 只收回入参列出的分组，其余授权保持不变。

### 5. 角色表只读，角色名即权限常量

- **角色不可增删改**：`mm_roles` 没有 create / update / delete 任何入口，
  角色集合由种子固定。角色名不是可编辑字段，而是**权限常量**。
- 由此，「改名等于改权限」的风险不复存在：角色名不变，权限就不变。
- 代价是**角色集合被冻结**：将来要新增「审计员」「只读运维」这类角色，
  必须走代码变更（种子 + `internal/transport/auth/roles.go` 的名字映射），
  不能在界面上点出来。
- 为防止有人直接改库里的角色名导致权限**静默失效**（名字对不上 → 该角色
  所有接口 403，而不是报错），**启动时校验角色表**：
  `transportauth.ValidateRoles` 比对库里的角色名与代码里的映射表，
  对不上直接拒绝启动并列出可用角色名。校验放在 `cmd/server/main.go`，
  在 `app.New` 完成缓存装载之后执行。
- 用户与角色的**绑定**仍然可改（`grantRoles` / `revokeRoles`）：
  角色实体是权限模板，用户是实例，模板不可变、实例可变是合理组合。

### 6. 用户权限取「直接授权 ∪ 角色继承」

- 一个用户对某个群集的生效权限 = **直接授权**（`USER_TO_CLUSTER` 边）
  **与** 角色继承（任一角色被授予该群集所属分组）的**并集**。
- 并集在授权方向上是单调的：加授权只会多、不会少，语义直观。
- 并集的固有性质是**没有「拒绝」**：撤销一个来源不等于撤销权限。
  想让用户不能访问某群集，必须两条路径都不通
  （撤直接授权 **且** 撤掉所有能覆盖该群集的角色分组授权）。
- 由此对管理面提出要求：界面必须区分**生效权限**与**权限来源**，
  否则管理员会误以为「取消勾选 = 断访问」。见下一节。

### 7. 人工审核走独立入口，审核人只审自己的工单

- 新增 `reviewTicket`（`Outcome: APPROVED | REJECTED`），取代原来让前端
  直接改状态的 `patchTicketStatus`：
  - **审核人身份**在 service 层校验：只有工单上挂的 `reviewer_id` 能审；
  - **状态**必须是「待人工审核」，其他状态一律拒绝；
  - **驳回必须带原因**，原因进操作日志（`ticket.reject`）。
- `patchTicketStatus` 保留但权限放宽到 `REVIEWER`，并只作为兼容入口；
  真正的审核语义统一走 `reviewTicket`，避免「谁都能把工单改成 LGTM」。
- 权限位：`reviewTicket` 需要 `REVIEWER` **或** `ADMIN`。
  原因是审核人是按工单指派的，可能持有的是 Root 角色而不是 Reviewer 角色，
  只认 Reviewer 会让「指派给我但我不是 Reviewer」的工单无法审核。
- 前端：**通过**用确认弹窗；**驳回**要填原因，走独立页面
  （沿用「表单走独立页面、确认才用弹窗」的约定）。

### 8. 管理面收敛到「系统设置」

- 新增一级入口「系统设置」，分五个页签：平台参数、群集分组、角色授权、
  用户授权、运行信息。原先孤立的「系统选项」并入平台参数页签。
- 分组的新建/编辑走独立页面，删除用确认弹窗。
- 角色授权（角色→分组）与用户授权（用户→群集）都按「勾选后整份提交」，
  后端是替换语义，提交一次即可，无需先收回。
- 管理类页签与导航项只对管理员显示；`用户与角色` 页签的账号清单同时
  提供新建、编辑、启用/停用。

## 后果

正面：

- 角色语义不再依赖自增 ID，权限与角色表解耦；
- 分组从标签变成真正的授权边界，「组间权限隔离」有了落点；
- 注册出来的账号默认拿到的是 `User` 角色而不是 `Viewer`；
- Root 不再能被误停用或被收走角色。

正面：

- 角色集合冻结后，权限语义稳定：不存在「某人改了角色名，某个团队
  突然全员 403」这种事；真要改，走代码评审。
- 启动期校验把「权限静默失效」变成「启动失败并说明原因」。

负面：

- 角色集合被冻结：新增角色类型必须改代码与种子，不能在界面上加。
- 角色→分组是「继承式」授权，用户可能同时拥有直接授权与继承授权，
  管理面需要把两层区分开（`GrantedClusters` 与 `Clusters`）。
- 并集语义没有「拒绝」：撤销一个授权来源后用户可能仍有权限，
  管理面必须显式呈现「生效权限」及其来源，否则管理员会误判。
- 平台参数页目前只能看不能改：种子里 14 条 SMTP/LDAP 选项全部
  `writable=0`，且运行时不读这些值，真正的邮件配置仍来自配置文件。
  页面按类型渲染并对密码项掩码，但要让它真正生效，还需要把
  邮件配置从配置文件迁到选项表（下一步）。

## 后续

- 邮件配置迁移到 `mm_options`（含加密存储与「发送测试邮件」），
  让平台参数页的 SMTP 段落真正可写；
- 「用户授权」页已展示生效权限与来源（直接 / 经由某角色的某分组），
  避免管理员把「取消直接授权」误当成「断访问」；
- 审核闭环已打通：工单详情页可审核通过/驳回、可写审核意见；
  后续可以补「审核意见的编辑/删除」与「审核记录的独立查询」；
- 若将来出现「临时冻结某用户对生产群的访问」这类需求，
  再引入第三条 `DENY` 边，语义变为 `直接 ∪ 分组 − 拒绝`；
  在此之前不预置拒绝语义。
